## Interpretación estricta

- **Formato:** éxito operativo para *Llama + JSON Schema*: la salida fue un objeto nativo parseable. Esto no permite atribuir el éxito exclusivamente a Llama, porque R1 con DeepSeek no usó el mismo modo estructurado.
- **Estructura:** fallo. Un objeto JSON bien formado no supera las pruebas de conservación. El modelo no distinguió suficientemente inventario físico de cuentas monetarias.
- **Identificabilidad:** los roles declarados desconocidos no se pueden tomar automáticamente como abstención correcta. La evidencia pública sí contenía una referencia nominal de capacidad y datos por ventanas, aunque no trazas completas de cola, cocina y despacho. Se debe comparar su abstención contra lo que las fuentes permiten sostener.
- **R1 vs. R2 no es un A/B controlado:** cambiaron modelo y modo de salida. R1 fue `FORMAT_REJECT` con 18,377 tokens de entrada y 2,128 de salida; R2 fue `IG_REJECT` con 14,803 y 796 tokens, respectivamente, y JSON mode. Los tokenizadores también pueden diferir.
- **No hay evidencia de recuperación causal correcta** con esta prueba. Tampoco la hay para declarar que un modelo sea mejor que el otro en razonamiento SD.

## Próxima decisión metodológica recomendada

No hacer otra inferencia de inmediato. Diseñar primero un contrato intermedio **entidad física/monetaria → stock/flow → extremos permitidos**, con reglas deterministas para impedir enlaces entre dominios incompatibles; preservar el grafo generado originalmente como señal de desempeño y distinguir la ayuda del validador de la capacidad propia del LLM. La oportunidad es evaluar si la partición de tareas aumenta corrección *causal*, no solo corrección de JSON. Cualquier R3 requerirá nueva autorización.
