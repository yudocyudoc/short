## Objetivo y controles

Se reutilizó exactamente el escenario C4, el contrato de JSON y las instrucciones iniciales sin alterar nada. Un mismo modelo produjo dos propuestas independientes, con `temperature=0.1`, `max_tokens=3500` y sin streaming:
- **prompt_only:** solicitud normal, sin `response_format`.
- **json_mode:** la misma solicitud con `response_format: {"type":"json_object"}`.

La ficha observacional C4 sólo fue usada por el verificador local. No se realizaron correcciones ni reintentos de IA. El diseño se documentó [antes de inferencia](../evaluation/protocol.md).

## Inspección post hoc (no reemplaza resultado primario)

Sin llamar de nuevo a DeepSeek, se tomó el texto **después de la primera etiqueta de cierre `</think>`**; se comprobó que el resto consistía exactamente en un bloque ```json ... ```. Se retiró sólo ese fence para que el validador C4 pudiera examinar el contenido, **sin modificar un solo número o flujo**.

El JSON final era parseable en ambos modos, **6/10, REJECT**.

| Puerta | Prompt normal | JSON Mode |
|---|:---:|:---:|
| G1 Esquema de JSON | ✓ | ✓ |
| G2 Stocks existentes (sólo inventario/pendientes) | ✓ | ✓ |
| G3 Seis flujos tipados | ✗ | ✗ |
| G4 Topología completa de solicitudes/material | ✗ | ✗ |
| G5 Totales de solicitudes | ✓ | ✓ |
| G6 Balance pendientes | ✓ | ✓ |
| G7 Balance de inventario con flujo material | ✗ | ✗ |
| G8 Capacidades/producción observada | ✓ | ✓ |
| G9 Acoplamiento solicitudes/material | ✗ | ✗ |
| G10 Incertidumbres/feedback | ✓ | ✓ |
| **Exploratorio** | **6/10** | **6/10** |

**Error compartido:** ambos JSON contienen cinco transiciones de solicitudes correctas y **no contienen ningún flujo de material**. Falta `{"entity":"material","from":"inventory","to":"consumed","total":21,"unit":"beverage_equivalent"}` como arista necesaria; este ejemplo se escribe **solamente tras ver las respuestas**, no se incluyó en los prompts. Por ello, aunque los stocks declarados son correctos —inventario inicial 30, final 9; aceptadas pendientes inicial 0, final 8— no existe trazabilidad formal de la reducción de materiales. El código marca G7 como fallida por falta de flujo, **no** por una resta incorrecta.

Ambas propuestas aciertan: 43 solicitudes totales, 9 rechazadas, 34 aceptadas, 5 canceladas, 21 entregadas y 8 pendientes; máquina 36 posibles, límite de insumos 30 y producción observada 21.

## Interpretación y decisión

1. **Hay JSON válido al final de cada respuesta**, pero separado por `<think>` y envuelto en un bloque Markdown. Para integrarlo en un software necesitaríamos que el proveedor entregue contenido final separado de razonamiento, o un parser de transporte cuidadosamente acotado y validado. No es correcto anunciar que JSON Mode ya resolvió el contrato de salida.
2. **Estructura SD parcial:** stocks y balances numéricos correctos en ambas respuestas, pero omitieron una transición material fundamental.
3. **Sin ventaja observable del JSON Mode** en esta pareja. Dos inferencias no bastan para hablar de confiabilidad o superioridad de modelos.
4. **No comparable causalmente con C4/GLM:** se cambió el modelo, JSON Mode se activó sólo en una condición y las salidas se examinaron con un diagnóstico post hoc distinto. Que DeepSeek haya obtenido 6/10 tras separación de razonamiento no significa que esté validado como constructor SD.

Recomendación: si se sigue trabajando con DeepSeek, diseñar un contrato de salida que separe reflexión y JSON final **en el origen** (proveedor) o con una capa de transporte preregistrada, más un mecanismo que verifique exhaustividad de relaciones materiales, sin inventar diagramas.
