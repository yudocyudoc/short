## Hechos y referencia del caso

- 3 horas, capacidad de máquina 10 bebidas/h → máximo de máquina **30**.
- Inventario inicial 24 bebidas-equivalentes → cota conjunta **24**.
- Producción y entregas observadas **16** → inventario final **8**.
- 33 solicitudes: **8 rechazadas antes de aceptación**, **25 aceptadas**; de éstas, **3 canceladas**, **16 completadas**, **6 aceptadas pendientes** al cierre.

## Resultado de la prueba preregistrada (estricta)

Ambas respuestas se entregaron dentro de un bloque Markdown ` ```json ... ``` `, aunque el contrato exigía un objeto JSON puro. El verificador no reescribe las salidas. Conforme a la rúbrica, ambas recibieron **REJECT, 0/10** por `G1_JSON` y las puertas dependientes quedaron sin evaluar.

**Esto es un fallo de interfaz de salida y NO demuestra por sí solo que los modelos fracasen en las diez propiedades estructurales.** El registro original y el resultado preregistrado no fueron modificados.

## Diagnóstico exploratorio post hoc (no sustituye el primario)

Un segundo workflow **no hizo llamadas al LLM**. Descargó los dos artefactos originales y eliminó **únicamente** el cerco Markdown exterior, sin modificar ninguna cifra, stock, ruta o texto del JSON. Aplicó entonces exactamente el mismo validador y los mismos hechos.

| Puerta | A: anterior | B: reglas SD |
|---|:---:|:---:|
| G1 JSON válido tras eliminar sólo cerco | ✓ | ✓ |
| G2 Stocks mínimos y sin ficticios | ✗ | ✗ |
| G3 Seis flujos tipados compatibles | ✗ | ✗ |
| G4 Rutas de solicitudes correctas | ✓ | ✓ |
| G5 Cantidades de solicitudes coherentes | ✗ | ✓ |
| G6 Balance final de pendientes | ✗ | ✗ |
| G7 Balance global material | ✗ | ✗ |
| G8 Capacidades y observado separados | ✓ | ✓ |
| G9 Acoplamiento entre material y entrega | ✗ | ✗ |
| G10 Marcas epistémicas y desconocidos | ✓ | ✓ |
| **Suma secundaria** | **4/10** | **5/10** |
| **Veredicto** | **REJECT** | **REJECT** |

**Precaución de lectura:** `G7_MATERIAL_BALANCE` depende de que `G2_STOCKS` pase; por tanto ambos fallaron G7 al introducir un tercer stock, **aunque ambos calculaban correctamente 24−16=8**. No se debe interpretar G7 por separado como incapacidad aritmética. Esta dependencia entre puertas deberá revisarse en un eventual validador v0.2, nunca retroactivamente.

### Fallos concretos observados

- **A:** añadió `prepared_stock` con 16 bebidas acumuladas a pesar de que toda bebida preparada se entrega de inmediato; añadió un flujo de material hacia ese stock. Declaró 22 solicitudes completadas (observado 16) y 3 pendientes (deben quedar 6).
- **B:** también añadió el stock ficticio `prepared_stock` con 16 bebidas, y un flujo extra cuya unidad es incompatible. Reconoció los 16 pedidos completados, pero puso **0 pendientes** en vez de 6 y conservó la estructura imposible de bebidas terminadas almacenadas.
- **Ambos:** capacidad de máquina 30, insumos 24, máximo conjunto 24 y 16 preparadas observadas correctos; inventario final 8 correcto; ninguna retroalimentación observada inventada (`feedback=[]`).

**Resumen epistemológico:** más reglas SD y un JSON tipado mejoraron algunas cifras internas, pero no bastaron para producir un grafo aceptable. El validador sí detectó fallas sin producirles una «corrección» que pareciera acierto del modelo. Esta prueba evalúa coherencia bajo datos dados, no recuperación de mecanismos causales reales.

## Decisión recomendada

Mantener C3 rechazado. Para la siguiente iteración, separar claramente:
(1) garantía de formato en la API (structured output o transport normalization preregistrada),  
(2) invariantes independientes de la forma, y  
(3) validez de stocks/rutas/cantidades. 

No añadir ecuaciones dinámicas hasta que una estructura mínima sea representable de forma coherente. No comparar los totales de C0–C3 como medidas de una misma población, ya que los escenarios, prompts y rúbricas cambian.
